# harness2 분석보고서 — Google Research Harness² 구조 분석 및 Hermes 적용 검토

- 작성일: 2026-10-18
- 대상: https://github.com/google-research/harness2 (커밋 `1cfe254`, 2026-10-13), 논문 arXiv:2610.14224
- DEV 번호: 미배정
- 성격: 조사·분석 (코드 변경 없음)

## 결론
1. harness2는 모델 가중치를 고정한 채 **하네스**(시스템 프롬프트·가드레일·메모리·도구 가이드·서브에이전트·
   스킬·스크립트·플러그인 8개 구성요소)를 과제마다 개선하는 연구용 프레임워크다. 정답(루브릭) 없이
   "같은 과제를 수정 하네스로 다시 돌려 보고 실행 궤적을 대조"하는 방식(Propose–Probe–Compose)이 핵심이다.
2. **Hermes를 그대로 꽂아 쓸 수는 없다.** 실행기(substrate)는 OpenCode/Codex 두 종만 있고,
   3개 벤치마크 어댑터가 `"oc"/"cx"`로 분기하며, 플러그인 경로 정규식(`.ts`)과 프롬프트 surface 텍스트도
   두 실행기 전용이다. Hermes 실행기를 추가하려면 harness2 코어 패치가 필요하다(§4).
3. Hermes의 구성요소는 8개 항목에 대부분 1:1 대응된다(§3). 특히 c8(훅)은 Hermes shell hook이
   Claude-Code식 `{"decision":"block"}`을 그대로 받아 harness2 Codex 훅 규약과 거의 같다.
4. Hermes에 실익이 큰 것은 코드가 아니라 **방법론**이다.
   - INV(절차)/DOM(도메인 지식) 분리 제안
   - 익명화된 산출물 기반 선택
   - `helped/hurt/no observed effect/confounded` 판정과 `cue/lesson/evidence/confidence` 교훈 기록
5. 권장 순서는 다음과 같다(§5).
   - 우선: 반복 cron 업무 1건 대상 소규모 오프라인 PoC(B안)와 교훈 기록 형식 차용(A안)
   - 보류: 벤치마크 점수가 필요할 때만 HermesSubstrate(C안)
6. **API 과금은 없다.** 운영 Hermes는 Codex app-server 런타임(ChatGPT/Codex 로그인)으로 모델을 호출한다.
   A·B안처럼 Hermes가 실행과 개선을 모두 맡으면 추가 과금이 없다. 소모되는 것은 구독 사용량 한도와 실행 시간이다.
   과금이 생기는 경우는 harness2 원본의 기본 경로(Vertex AI 실행기·채점기)를 그대로 쓸 때뿐이다(C안).
7. **개선·선택·회고 세션은 구독 중인 Claude CLI(`claude -p`)로 돌린다.** 실행은 Codex 구독, 개선은 Claude 구독으로
   나뉘어 추가 과금이 없고 한쪽 한도에 몰리지 않는다. 단, harness2 원본의 `claude_cli` 채널은 Vertex 과금으로
   고정돼 있어 그대로는 구독을 쓰지 않는다(§2-6).

## 1. harness2 개요
- 정의: "하네스" = 모델을 에이전트로 동작시키는 주변 시스템. "하네싱" = 그 시스템의 최적화.
- 두 단계 재귀.
  - **과제 단위 재귀**: 현재 과제의 실행 하네스를 Propose–Probe–Compose로 개선한다. 정답 피드백은 쓰지 않는다.
  - **하네싱 단위 재귀**: 채택된 하네스와 증거 기반 교훈을 도메인별 라이브러리에 쌓아 다음 과제의 개선에 쓴다.
- 지원 범위
  - 모드: parallel / sequential
  - 실행기: OpenCode(기본) / Codex(`--substrate cx`)
  - 벤치마크: JobBench / LAB(법률) / WorkBuddy-Bench
- 보고 성과(README): 1스텝 적용으로 GLM-5, Gemini 3.5 Flash 기반 하네스 대비 향상.
  WorkBuddy-Bench 최대 +11.5점, JobBench +4.5점, LAB 부분 통과율 +11.8%p.
- 규모: Python 약 12.7k LOC, 런타임 의존성 없음(`dependencies = []`). 렌더/브릿지만 extras.

## 2. harness2 동작 구조 (코드 기준)

### 2-1. 편집 대상: 하네스 트리 c1..c8 (`harness2/core/tree.py`)
하네스는 "경로 → 파일 내용" 딕셔너리(`Tree`)다. 실행기별 차이는 `SurfaceSpec` 데이터(경로·상한)에만 있다.

| 구성요소 | OpenCode 경로 | Codex 경로 | 컨텍스트 적재 |
|---|---|---|---|
| c1 시스템 프롬프트 | `systemprompt.md` | `AGENTS.md` | 상시(always-on) |
| c2 가드레일 | `guardrails.md` | (AGENTS.md에 포함) | 상시 |
| c3 메모리 | `LongTermMEMORY.md` | (AGENTS.md에 포함) | 상시 |
| c4 도구 가이드 | `tool_descriptions/tool_guidance.md` | (AGENTS.md에 포함) | 상시 |
| c5 서브에이전트 | `sub_agents/<name>/AGENT.md` | 동일 → `[agents.<name>]` 역할로 설치 | 별도 컨텍스트 |
| c6 스킬 | `skills/<name>/SKILL.md` | `.agents/skills/<name>/SKILL.md` | 온디맨드 |
| c7 스크립트 | `scripts/<name>.py` | 동일 | 온디맨드(bash) |
| c8 플러그인/훅 | `plugin/<name>.ts` | `.codex/hooks.json` | 도구 루프 내부 |

- 상시 텍스트 상한: OpenCode 24,000자, Codex 8,000자(Codex는 32,768바이트에서 무음 절단).
- 스킬은 상시 텍스트에 트리거 문장이 없으면 검증에서 탈락한다. `autotrigger()`가 이를 자동 보정한다.
- 경로 탈출(`..`, 절대경로)은 거부한다. 허용 경로 밖의 파일은 반영하지 않고 재시도 사유로 돌려준다.

### 2-2. 과제 단위 재귀: Propose–Probe–Compose (`core/recursion.py`)
1. **Base**: 기본 하네스로 같은 과제를 k번 실행한다(참조 실행).
2. **Propose**: 개선기(improver) 세션이 증거 디렉터리를 읽고 하네스 파일을 직접 편집한다.
   - `INV`(절차 차원): 도구 오류 처리, 반복 작업의 스크립트화, 완료 확인 등 "어떻게 일하는가".
   - `DOM`(도메인 차원): 산출물 계약, 판단 규칙, 실무자 지식 등 "무엇을 아는가".
   - 프롬프트로 두 차원의 영역을 갈라, 서로의 영역을 건드리지 못하게 한다.
3. **Probe**: 제안된 하네스마다 같은 과제를 실제로 다시 실행한다.
4. **Compose**: 후보 하네스와 그 실행 궤적을 대조(behavioral contrast)해 최종 하네스를 합성한다.
5. 무효 제안은 1회 재시도하고, 그래도 무효면 현 하네스로 폴백한다. `KEEP_BASE`(변경 없음)도 정당한 답으로 인정한다.

| 모드 | 흐름 | 실행(rollout) | 개선 세션 |
|---|---|---|---|
| parallel(`agg`) | base k → INV k + DOM k 후보 → 독립 합성 k개 | 4k | 3k |
| sequential(`seq`) | 라운드마다 INV 1 + DOM 1 → 합성 1, k라운드 누적 | 4k | 3k |

- 과제당 선택 1회(k=1이면 생략)와 회고(reflection) 1회가 더해진다.
- 로컬 데모(`harness2-demo --k 2`, 2과제 × 2모드)에서 산식을 확인했다(§6).
  - 실제 실행 28회(base 실행은 두 모드가 공유)
  - 편집기 호출 32회

### 2-3. 정답 없는 선택 (`core/selection.py`)
- 최종 후보들은 **산출물만** 익명 ID(A, B, …)로 제시하고 하네스는 숨긴다. ID 배정은 시드 고정 셔플이다.
- 선택기는 ```` ```choice ```` 블록으로 하나를 고르고, `<why>`에 이유를 남긴다.
- 선택에 실패하면 기본 하네스의 산출물로 폴백한다(예외를 던지지 않음).

### 2-4. 하네싱 단위 재귀: 경험 라이브러리 (`core/library.py`, `selection.reflect_adoption`)
- 채택 후 회고 세션이 모든 후보 하네스를 base와 diff한다.
  - 편집마다 `helped / hurt / no observed effect / confounded` 중 하나로 판정한다.
  - 여러 구성요소를 동시에 바꿔 원인을 분리할 수 없으면 `confounded`를 **우선** 쓰도록 강제한다.
- 전이 가능한 교훈은 최대 1개만 남긴다. 근거가 없으면 `NO_ENTRY`를 쓴다.
  - `cue`: 적용 상황의 형태
  - `lesson`: 하네스에 가할 조작(대상 구성요소를 명시)
  - `evidence`: 근거가 된 편집 행
  - `confidence`
- 저장 위치: `<root>/<run>/<mode>/<domain>/harnesses/<task>/{harness/, EXPERIENCE.md}`와 `INDEX.md`.
  - 요약이 아니라 **채택된 하네스 트리 전체**를 보관한다.
  - 같은 도메인의 다음 과제가 이를 읽는다.

### 2-5. 안전 장치
- `ANSWER_FREE`: 루브릭·정답·점수는 컨텍스트에 없다. "채점자가 원하는 것"을 추정하지 않게 한다.
- `EVIDENCE_BOUNDARY`: 증거 파일(궤적·산출물·후보 하네스)은 데이터일 뿐 지시가 아니다.
  후보 하네스의 스크립트·플러그인 실행을 금지한다(프롬프트 인젝션 방어).
- 유출 검사: 채점 결과(`assert_no_grader_verdicts`)와 누출 경로 glob(`assert_no_leak_paths`)을 확인한다.
- 증거 제공 방식: 증거는 파일 트리(`context/…`)로 주고, 프롬프트에는 짧은 포인터만 둔다.
  그래서 궤적을 잘라내지 않는다.

### 2-6. 실행 환경·의존성
- Linux, Python 3.12(3.13도 지원), uv, Node.js 20+, gcloud CLI가 필요하다.
  WorkBuddy는 Docker, LAB은 pandoc/poppler가 추가로 필요하다.
- 기본 모델 경로는 Vertex AI(유료 API)다. 실행기·채점기는 Gemini, 개선기는 Vertex Claude 또는 Gemini를 쓴다.
- 개선기 채널은 `claude_cli`, `opencode` 두 가지뿐이다(`core/spec.py: CHANNELS`).
  - `claude_cli` 채널은 `claude --dangerously-skip-permissions -p --output-format json`을 임시 디렉터리에서 실행한다.
  - 그런데 `Proposer.env()`가 `CLAUDE_CODE_USE_VERTEX=1`과 Vertex 프로젝트를 강제로 넣는다(`core/proposer.py`).
    그래서 구독 로그인이 아니라 Vertex(GCP 프로젝트)로 과금된다.
  - 기본 채널도 `config.py`의 `DEFAULT_PROPOSER_CHANNEL = "opencode"`로 고정이고, 3개 벤치마크가
    `resolve_channel_model(None, None)`으로 이 값을 쓴다. CLI 플래그로는 `claude_cli`를 고를 수 없다.
  - `ANTHROPIC_API_KEY` 등은 이미 `_DROP_ENV`로 제거하므로, 위 두 곳만 고치면 CLI 로그인 계정(구독)으로 동작한다.
    예: `DEFAULT_PROPOSER_CHANNEL`을 환경변수로 받고, 구독 모드에서는 `env()`가 `ANTHROPIC_MODEL`만 넣게 한다.
- 실행기 네트워크는 무제한이고 Codex는 샌드박스가 비활성이다. 문서가 공개 루브릭 유출 위험을 직접 경고한다.
- 라이선스: Apache-2.0. `third_party/`는 각 상류 라이선스를 따른다.

## 3. Hermes 구성요소 대응표

| harness2 | Hermes 대응 | 적재 방식 | 상한 |
|---|---|---|---|
| c1 시스템 프롬프트 | `$HERMES_HOME/SOUL.md`(identity 슬롯), 컨텍스트 파일 1개 | 시스템 프롬프트, 세션당 1회 빌드·캐시 | 20,000자/소스, 앞 70%·뒤 20% 절단 |
| c2 가드레일 | 전용 프롬프트 블록 없음. 코드 레벨 장치로 대체 | 승인 요청·도구 결과 경고 | — |
| c3 메모리 | `$HERMES_HOME/memories/MEMORY.md`, `USER.md`, 외부 provider 1개 | 시스템 프롬프트 volatile tier, 세션 시작 스냅샷 | 2,200자 / 1,375자, 초과 시 쓰기 거부 |
| c4 도구 가이드 | `prompt_builder.py` 상수 | 시스템 프롬프트 stable tier(도구 로드 여부로 게이트) | — |
| c5 서브에이전트 | `delegate_task`. **역할 정의 파일 없음**, 호출 시 `goal/context/toolsets/role` | 자식은 컨텍스트 파일·메모리 미적재 | depth 1, 동시 3, 50회 반복 |
| c6 스킬 | `$HERMES_HOME/skills/**/SKILL.md`, `skills.external_dirs` | 인덱스는 stable tier, 본문은 `skill_view`로 온디맨드 | 인덱스 설명 60자 절단, 본문 100k자 |
| c7 스크립트 | 스킬 `scripts/`(terminal로 실행), `execute_code` | 온디맨드 | 도구 출력 50KB |
| c8 플러그인/훅 | Python 플러그인 훅, shell hook(config.yaml `hooks:`) | 도구 루프 내부 | shell hook 60s(최대 300s) |

표 보충:
- c1 컨텍스트 파일은 `.hermes.md`, `AGENTS.md`, `CLAUDE.md`, `.cursorrules` 중 처음 찾은 1개만 적재한다.
  상한은 `agent/prompt_builder.py:875`의 `CONTEXT_FILE_MAX_CHARS`다.
- c2 코드 레벨 장치는 세 가지다.
  - `tools/approval.py`: HARDLINE은 항상 차단, DANGEROUS는 승인 요청
  - `agent/tool_guardrails.py`: 도구 루프 경고
  - `tools/threat_patterns.py`: 인젝션 스캔
- c3 상한은 `tools/memory_tool.py:124`에 있다.
- c4 상수 예: `MEMORY_GUIDANCE`, `SKILLS_GUIDANCE`, `TOOL_USE_ENFORCEMENT_GUIDANCE`(모델별).
- c6 인덱스 설명 60자 절단은 `agent/skill_utils.py:523`에 있다.
- c8 훅 상세
  - Python 훅: `pre_tool_call`은 차단, `pre_llm_call`은 컨텍스트 주입, `transform_tool_result`는 결과 교체를 할 수 있다.
  - shell hook은 `{"decision":"block","reason":…}`을 수용한다(`agent/shell_hooks.py:28-50`).

차이가 큰 지점:
- **c2·c4는 Hermes에서 사용자 편집 파일이 아니다.** 가드레일은 코드(승인·도구 가드)이고, 도구 가이드는
  `prompt_builder.py`에 하드코딩되어 있다. 하네스로 편집하려면 Codex surface처럼 SOUL.md나
  컨텍스트 파일 한 곳에 접어 넣어야 한다.
- **c3 상한이 훨씬 작다.** harness2는 24,000자 상시 예산 안에서 메모리를 쓰지만, Hermes는 MEMORY.md
  2,200자에서 쓰기를 거부한다. DOM 제안이 메모리를 키우면 그대로 실패한다.
- **c5 대응 파일이 없다.** `sub_agents/<name>/AGENT.md`에 해당하는 것이 없다. "delegate_task 호출
  템플릿을 담은 스킬"로 대체하거나, JobBench Codex처럼 `allow_subagents=False`로 둬야 한다.
- **c6 트리거 보정이 불필요하다.** Hermes는 스킬 인덱스를 자동으로 시스템 프롬프트에 넣으므로
  harness2의 `autotrigger()`가 필요 없다. 다만 설명이 60자로 잘리므로 설명 품질이 곧 트리거 품질이다.
- **c8 훅 규약이 거의 같다.** Codex `hooks.json`의 `PostToolUse → {"decision":"block"}` 규약이
  Hermes shell hook과 거의 같아 이식이 쉽다.
- 세션 중 변경 금지(프롬프트 캐시 정책)와는 충돌하지 않는다. harness2의 하네스 변경은 **실행과 실행 사이**에만
  일어나기 때문이다.

## 4. 직접 통합(HermesSubstrate) 시 필요한 작업
harness2의 `Substrate` 프로토콜(`surface/materialise/execute/read_trajectory/preflight`)은 일반적이지만,
아래 지점은 "데이터 추가"가 아니라 **harness2 코어 수정**이 필요하다.

| 위치 | 현재 | 필요 변경 |
|---|---|---|
| `core/tree.py: _res()` | 플러그인 경로 `<plugin_dir>/<name>.ts`로 고정 | Hermes Python 플러그인(`plugins/<name>/{plugin.yaml,__init__.py}`) 또는 shell hook 파일 허용 |
| `core/prompts.py: _build_surface_texts()` | `opencode`, `codex` 두 surface 설명문만 | Hermes surface 설명문(구성요소 표·상한·우선순위) 추가 |
| `benchmarks/{jobbench,lab,workbuddy}.py` | `"oc"/"cx"` 분기, 런처·설치 모드·궤적 파일명 고정 | 벤치마크별 Hermes 런처 3종 |
| `core/spec.py: CHANNELS` | 개선기 `claude_cli`, `opencode`만 | (선택) Hermes를 개선기로도 쓰려면 채널 추가 |

Hermes 쪽 구현 스케치:
- `materialise`
  - 격리된 `HERMES_HOME`에 `SOUL.md`, `memories/MEMORY.md`, `skills/<name>/`, `plugins/`를 배치한다.
  - `config.yaml`에는 모델 설정과 `hooks:`를 병합한다.
  - 경로는 `hermes_constants.get_hermes_home()`가 `HERMES_HOME`을 따르므로 이것으로 격리된다.
- `execute`: `HERMES_HOME=<staging> hermes chat -q "<task>" -Q --yolo -t <toolsets>`를 실행한다.
  - 대안은 `hermes -z`다. 다만 컨텍스트 파일·메모리를 그대로 적재하므로 작업 디렉터리를 통제해야 한다.
- `read_trajectory`
  - hermes CLI에는 `save_trajectories` 플래그가 없다.
  - 대신 `$HERMES_HOME/state.db`(`sessions`·`messages` 테이블)에서 세션을 읽어 공통 문법으로 렌더한다.
  - 또는 `AIAgent(save_trajectories=True)`의 ShareGPT 포맷을 쓴다.
- surface 정의는 CODEX_SURFACE처럼 단일 상시 파일 모델이 맞다.
  예: `always_on=("SOUL.md","memories/MEMORY.md")`. 메모리 2,200자 상한은 `validate`에 반영해야 한다.

판단: 3개 벤치마크 런처 + 코어 패치 + 궤적 렌더러가 필요해 **수 일 이상 규모**다. 상류(harness2)에 기여하지 않으면
포크를 유지해야 한다. 점수 비교가 목적일 때만 의미가 있다.

## 5. 적용 방안 (우선순위)

### A안 — 교훈 기록 형식 차용 (작업량 작음)
- 대상: 에이전트가 스킬을 만들고 고치는 경로(`skill_manage`, `agent/background_review.py`)와
  curator 리뷰(`agent/curator.py:330` `CURATOR_REVIEW_PROMPT`).
- 차용할 것
  - 편집별 판정(`helped/hurt/no observed effect/confounded`)
  - `cue/lesson/evidence/confidence`
  - 근거가 없으면 `NO_ENTRY`
  - 동시 변경이면 `confounded`
- 효과: 현재 curator는 사용 빈도·유휴 기간과 LLM 판단으로 통합·보관하고, 근거 요구가 없다.
  증거 형식을 요구하면 근거 없는 스킬 병합·교훈 누적을 줄일 수 있다.
- 주의: curator 프롬프트는 코어 파일이다. 로컬 포크에서만 바꿀지 상류 PR로 낼지 먼저 정해야 한다.
  플러그인으로 하려면 `pre_llm_call` 컨텍스트 주입으로 형식만 안내하는 정도가 한계다.

### B안 — 반복 업무 대상 오프라인 Propose–Probe–Compose PoC (작업량 중간, 권장)
- 근거: 06:00 아침 브리핑, 일일 안전브리핑 3종 같은 cron 업무는 "같은 도메인의 반복 과제"다.
  harness2의 하네싱 단위 재귀(도메인 라이브러리)가 노리는 상황과 정확히 같다.
- 절차(k=1, 실행 4회, 개선 세션 3회와 회고 1회)
  1. 운영 프로필을 복제해 격리 `HERMES_HOME`을 만든다.
     - `hermes profile create`를 쓰거나 디렉터리를 복사한다.
     - **전송 도구를 제외한다**(`-t`로 toolset 제한, 아래 주의 참고).
  2. base 실행: cron 프롬프트를 `hermes chat -q … -Q`로 실행하고 산출물과 세션을 수집한다.
  3. INV·DOM 제안: 개선기는 구독 중인 Claude CLI(`claude -p`)를 쓴다(권장, 대안은 Hermes 자체).
     실행기(Hermes/Codex)와 모델 계열이 달라 논문 구성(실행기 Gemini·GLM, 개선기 Claude)과도 맞다.
     개선기는 다음 파일만 편집한다.
     - SOUL.md
     - 해당 업무 스킬의 SKILL.md와 scripts/
     - MEMORY.md(2,200자 이내)
  4. 후보마다 같은 프롬프트로 재실행한다. 산출물을 익명화해 선택하고, 채택된 하네스와
     EXPERIENCE.md를 라이브러리에 보관한다. 선택·회고 세션도 Claude CLI로 돌린다.
- 구현 형태
  - 코어를 수정하지 않는다(플러그인 규칙 준수).
  - `~/.hermes/plugins/<name>/`의 `ctx.register_cli_command`나 독립 스크립트로 구현한다.
  - harness2의 `core/{recursion,selection,library}.py`는 Apache-2.0이므로 고지를 붙여 차용할 수 있다.
- 주의
  - cron 경로에서 돌리면 텔레그램으로 실제 전송된다. 반드시 CLI 경로와 격리 프로필에서 실행한다.
  - API 과금은 없다. 실행 4k회는 Codex 구독에서, 개선 3k회와 선택·회고는 Claude 구독 사용량에서 나간다.
    k=1이면 Hermes 실행 4회, Claude CLI 세션 4회(개선 3, 회고 1)다. k=1부터 시작한다.
  - Claude CLI는 환경에 `ANTHROPIC_API_KEY`가 있으면 로그인 상태여도 구독 대신 그 API 키로 과금된다.
    `CLAUDE_CODE_USE_VERTEX`/`CLAUDE_CODE_USE_BEDROCK`도 마찬가지다. 실행 스크립트에서 이 변수들을 제거하고 돌린다.
  - 같은 날 데이터로 재실행해야 대조가 성립한다. 날씨·일정처럼 시점에 의존하는 입력은 base 실행 시 스냅샷한다.

### C안 — HermesSubstrate (작업량 큼, 보류)
§4의 작업 전부가 필요하다. JobBench/LAB/WorkBuddy 점수로 Hermes 하네스를 객관 비교해야 할 때만 착수한다.
개선기는 §2-6의 패치로 Claude 구독을 쓸 수 있다. 하지만 harness2 원본은 채점기가 Vertex AI 유료 API 기본이므로,
채점기를 구독 경로로 바꾸지 않으면 세 안 중 유일하게 과금이 생긴다.

### 비권장 — 대화 중 실시간 자가 개선
- 과제마다 4k 실행이 필요하므로 대화 지연과 구독 사용량 소모가 감당되지 않는다.
- 세션 중에 하네스를 바꾸면 프롬프트 캐시 정책(AGENTS.md "Prompt Caching Must Not Break")을 위반한다.
- 하네스 변경은 다음 세션부터 적용하는 지연(deferred) 방식만 허용된다.

## 6. 검증 내역
- harness2 클론(커밋 `1cfe254`) 후 코어 모듈 정독
  - `core/{tree,recursion,selection,library,context,prompts,schedule,spec}.py`
  - `substrate/{base,opencode,codex}.py`
- 오프라인 데모 실행: `harness2-demo --k 2`(모델 자격증명 불필요, 결정적 편집기)
  - 결과: 2과제 완료, 0 실패, 실행 28회, 편집기 호출 32회
  - 산식 대조: 과제당 base 2 + parallel 6 + sequential 6 = 14, 2과제 → 28.
    편집기 호출은 (3k + 선택 1 + 회고 1) × 2모드 × 2과제 = 32.
  - 라이브러리에 `EXPERIENCE.md`(편집 판정 `helped`와 cue/lesson/evidence/confidence)가 생성되는 것을 확인했다.
- Hermes 측 수치·경로는 소스에서 직접 확인했다.
  - `CONTEXT_FILE_MAX_CHARS`
  - 메모리 상한
  - 스킬 설명 60자 절단
  - curator 기본값 7일/2시간/30일/90일
  - `VALID_HOOKS`
  - shell hook 규약
  - `-z/--oneshot`
- 이 보고서는 문서만 추가한다. 코드 변경은 없고, 테스트 대상도 없다.

## 7. 후속
1. A·B·C 중 착수안을 결정한다. 권장은 B안 PoC(업무 1건, k=1)와 A안 형식 차용이다.
2. B안 착수 시 대상 cron 잡 1건을 지정한다. 격리 프로필에서 전송 도구를 제외했는지 먼저 확인한다.
3. C안이 필요하면 harness2 상류에 "substrate 플러그인화"(plugin 경로 정규식, surface 텍스트 등록 API)를
   먼저 제안하는 편이 포크 유지보다 낫다.
